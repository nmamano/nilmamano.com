The thesis of this post is that RL environments are the third and latest wave of RL data, and the current focus of a lot of investment in AI. The post explains this shift.

## Act I: How models are trained

### Overview

The standard AI model today is the Transformer. It's the next word predictor. Basically tokens in and tokens out.

Almost all models being trained today/driving the top startups, including LLMs, are just very, very large Transformers. That's it.

And while the high-level Transformer architecture has evolved (e.g., MoE), it still looks similar to the original one from 2017.

So, what has changed?

One is, obviously, the Transformers have gotten bigger. We scaled compute.

Two is, we are putting in more and more data. And this is a huge industry.

Big labs — OpenAI, Anthropic, xAI, Meta, and to some extent Microsoft and Amazon — are spending in the billions on data acquisition. They throw serious money around to get data to train models.

That's why there are dozens of companies generating this data, and many are making a lot of money.

**What does data look like these days?**

Before getting into that, it'll be helpful to talk about the training process.

There are 3 stages.

1. Pre-training.
2. What's called mid-training, or SFT, supervised fine-tuning.
3. RL, which is also called post-training.

#### Pre-training

Essentially, you take the entire corpus of the entire internet and anything else you can have, books, everything you can scrape.

These datasets can be in the terabytes - trillions of tokens.

You put it in the model, and it learns to predict the next token, but it also learns the structure of all the text.

The pre-trained model is called a base model.

The base model is literally an autocomplete. You type something and it will just complete your sentence.

It doesn't really know how to answer questions. It doesn't know how to do sophisticated tasks like tool use and coding.

Next, the companies need to make these base models useful.

#### Supervised fine-tuning

That's when **supervised fine-tuning** comes in.

That basically is, you put in specialized data. That specialized data could be domain specific data.

So for example, if I want my model to be good at finance and science, I can put in specialized finance data and science data. And since this comes after pre-training and training has a recency bias, the model is more sensitive to finance and science.

Part of supervised fine-tuning is called **instruction following**. That's the question answer format.

We give it a lot of examples of question, answer, question, answer, question, answer, question, answer. And then eventually the model sees so many of these that when it sees the question, it knows to output the response in an answer format.

It's called _supervised_ because, following the classic ML taxonomy, every "input" (question) has an explicit, human-provided "label" (answer).

The reason why it's called fine-tuning, and we're not at RL yet, is that it's the same process as pre-training: you have these curated datasets with specific formats, and the model learns the formats from them.

#### RL

Now you get into RL. There are different types, like:

- Verifier RL for the reasoning side - math, coding, objective things.
- Human feedback RL for subjective things.

Typically, you do the objective stuff first and you spend a lot of compute on it - as much compute as for training. So you can train this RL for months, and you need a lot of highly sophisticated math and reasoning data to do this RL.

That's how you get models that do super well at math and science benchmarks: they spent a ton of money buying data from real mathematicians and researchers, and then they post-train the heck out of the model.

And then you have the subjective stuff, like safety and creative writing. What's the model's personality? How does it speak? Is it unbiased? 

All that soft stuff is at the end.

Verifier RL and RLHF are done via slightly different RL processes, but they are both RL processes.

We'll first talk about RL itself, and then about how it's applied to these cases.

<Callout>
"Does RL modify the same weights in the model as training and supervised fine-tuning?"

There are 2 variations.

That depends on the goal.

If you want to fundamentally uplift the model in science or whatever - then you bake it into the model.

But there's also a technique called LoRA (low rank adapters) where you train an independent set of weights, and then you can optionally add those weights to the model to customize its behavior.

(LoRA trains two smaller matrices which, when multiplied, produce a matrix with the same shape as the ones in the model, and then it's literally element-wise addition.)

So, during RL, you can train only the LoRA weights and not the main model weights.

And then you can swap out the LoRA weights, and you can get a lot of different, e.g., personalities, by using the same base model and different added LoRA weights.

That's how people do the more cosmetic stuff.
</Callout>

### RL Overview

RL, reinforcement learning, is a learning strategy based on doing a bunch of simulations and obtaining rewards.

We can think of the model itself as a "policy" that maps a state (the system prompt) to actions (the continuations).

Let's say the model is trying to answer a math problem.

We can call ChatGPT 1000 times to answer this math problem. That's called 1000 "rollouts" of the policy.

Sometimes it gets it right, sometimes it gets it wrong. Based on how often it gets it right, you get a score for how smart the current model is.

RL is the process by which you take the right responses and upgrade the weights that correspond to those, while downgrading the weights corresponding to the wrong responses.

There are several variants of this.

#### DPO 

The easiest variant is DPO, direct preference optimization.

Have you used ChatGPT and gotten, "here's response A and response B, which do you like better?"

That's DPO: you have 2 examples (rollouts), you pick one, and DPO increases the weight on the one you like better, and decreases the weight on the one you like worse.

People do this for a lot of things: safety, personality, vibes, aesthetics, and so forth.

The good thing about DPO is that it's an _offline_ training method: the model doesn't need to run at all during training - the user preference becomes training data directly.

Generating a ton of preference data is what Scale AI used to do.
They created giant datasets of positive and negative examples, and then companies can DPO their models on this dataset, offline.

DPO is kind of like fine-tuning in that you train the model offline. Online RL is more complicated.

#### GRPO

The 2nd type of RL, GRPO (Group Relative Policy Optimization), is used for more objective tasks like math and science. It was created by DeepSeek.

Let's say you want your model to be good at math.

A good proxy for that is that it can solve questions from some math competitions.

So, we can take a dataset of contest questions, and, for each one, do a couple hundred runs of the model trying to solve it.

Some rollouts are correct, some are wrong.

For GRPO to work, we need the model to get it right at least some times, ideally in a middle band (roughly 20-50%). So the questions can't be too easy or too hard.

All the AI labs now want data like this: domain-specific tasks - like math problems - where the model gets the task correct in that middle band, because you have positive signal for training but it's not saturated.

If the model gets it right too often, you need harder tasks.

In a typical setup, GRPO might do, say, 64-256 rollouts per question. Let's keep using 200 as a concrete example and calculate a score called an _advantage function_ for each one.

The advantage function is how much better this rollout is compared to the average.

If 50% of rollouts are correct, a correct rollout gets a modest positive advantage.

But if only 10% are correct, a correct run gets a much larger positive advantage.

Based on this advantage function, we backpropagate the weights.

There's a certain loss function that I forget, but I have a Notion doc where I spell all this out.

Unlike DPO, GRPO is an online training algorithm - it takes time. Doing a batch of 200 rollouts may take a couple of minutes.

These days, the kind of tasks trained with GRPO for coding agents are end-to-end coding tasks. Then there's some grader that determines if the task was completed correctly or not.

The dataset size may be in the 100s to 1000s of high-quality tasks, so they are not huge.

And for every one of them, the model will do 200 simulations, and each of these simulated runs will take like 1000 steps.

So the total number of tokens generated can be approximated by 1000 * 200 * 1000, and from that, we get 1000 * 200 scores to train on.

Training may go over the dataset twice.

Compared to pre-training and supervised fine-tuning, which take months, this RL stuff only takes a couple of days.

#### PPO

This is the most complicated one, and the original version that OpenAI used back in the day.

PPO usually uses a value model (a critic) to estimate baseline values, then computes advantage from that.

Many teams use simpler alternatives in practice because PPO can be cumbersome, so we won't get into it.

### Expert networks

Now, there are companies like [Mercor](https://mercor.com), which are expert networks.
If a company wants their model to be good at archaeology, they can go to Mercor and pay archaeologists to generate or annotate suitable training data.

The archaeologists are gig workers, from grad students to professionals, and can get paid to write questions and answers about archaeology, or write some archaeology tests.

To prove it understands archaeology, the model tries to do the tests and gets judged against the answers. That's what we need for RL and, more precisely, GRPO.

Expert networks can cover every niche of human knowledge, and that's how we get models that are pretty good at many distinct domains.

## Act II: RL environments in practice

### 3rd Wave of RL

Increasingly, the labs care about their models being good at what they call economically valuable tasks. Things like finance, accounting, insurance, healthcare. A lot of office work.

There's even "whole company simulation," where the goal is to train agents in _every_ task across an entire company.

So far, software engineering has been the main one. There's a benchmark called SWE-Bench, which is basically a lot of hard software engineering tasks.

These days, models can write code fine. So now it's about end-to-end software engineering workflows. SRE, deployment, etc. It's about making architecture and design decisions and then writing software end to end and then testing it and pushing it to GitHub. We need RL tasks that simulate all of that.

So now, instead of sourcing data from experts, we source it from real companies, or at least from contractors doing actual work.

- Originally, it was, "Here's all the text we found" (pre-training).
- Then, "Here's some advanced scientific data" (supervised fine-tuning).
- First RL wave (Scale AI): "Here's some preference data from human labelers" (DPO RL).
- Second RL wave (Mercor / expert networks): "Here are questions and answers generated by experts." (GRPO RL).
- Third RL wave: "Here are tasks done by real workers." (also GRPO RL).

<Callout>
Part of being able to do economically valuable tasks is being able to literally control a computer.

Computer use, browser use, and terminal use are 3 dimensions of that.

Computer use is normally terminal-based. There's a benchmark for that called Terminal-Bench. There's also a version called OS World, which gives the model access to the pixels on the screen.

Browser use is typically based on Chrome.
</Callout>

### RL Data Companies

So, how do we formulate the tasks needed to RL agentic behaviors on economically valuable tasks?

These are models that have already been trained to operate tools, write code, and operate agentically.

There are _data environment companies_ which focus on generating these specialized tasks.

The tasks should be to do some end-to-end workflow that is economically valuable.
Doing a financial analysis, handling a complicated logistics scheduling problem, managing emails with various stakeholders, or writing a report.

These are real tasks, and the real people doing these tasks are basically (and usually unknowingly) generating data and annotating it for free as part of their work.

For example, for whole-company simulation, tasks can be created from a company's entire email history and every project they've ever done.

### RL Environments

An _RL environment_ is a sandboxed environment where an agent tries to complete these tasks.

RL environments are also called RL gyms or AI training gyms. 

These environments are typically a Docker container with:

#### 1. Pre-installed software

Say the task requires tools like Microsoft Word. The Docker container doesn't have Microsoft Word, but we can install LibreOffice or some open-source variant.

The task may require Slack. We don't have Slack, but we can install an open-source version like Mattermost.

And so on. You need GitHub? We can attach the Docker container to GitHub.

It is a real simulated work environment.

#### 2. Data

The data has to be realistic, so it has to come from some real-world source. That's why big labs and startups alike are going to big companies across different domains and asking them to sell data.

#### 3. Tool APIs

You need an API spec for the tools that the agent can call.

The APIs these days are MCPs, which are basically an API with a description that tells the agent when to call each API.

For example, the slack API covers the operations in Slack: open a channel, close a channel, talk to a person, read a channel, look at a person's profile, etc.

These are the API calls that the model is trying to learn for tasks involving Slack.

In a Docker container, what we can do is build a wrapper around the open-source version of Slack so that, to the model, it can look exactly the same.


#### 4. A harness

Whenever the model outputs tokens corresponding to a tool call, there needs to be a layer above it pausing the generation, running the corresponding operation, and resuming the agent with the appropriate output. That's the harness. There's a lot more to it, but think "Claude Code". That's the thing that we unleash in the environment, not just Opus 4.7.

#### The tasks

So we create these Docker environments with very specialized settings.

Then we need tasks for the model to attempt in them.

The tasks are also sourced from contractors or experts based on realistic tasks.
They need to specify the goal (which becomes the task's starting prompt) and provide the official solution.

We may ask the expert, "If you did this Excel model well, what would the final sheet look like?"

Typically you want 100s of environments. Each of these can have multiple tasks (always run in isolation).

This means we still need a lot of expert annotators, as well as engineers to set up the environments and tasks. That's what a lot of the new AI companies focus on.

### Grading

So, every rollout is a full end-to-end run where it spins up a Docker container.

Eventually, the outcome needs to be plugged into a GRPO trainer, so they need to have a score.

Let's get to the grading.

The idea is that a human expert creates a rubric.

The framework is often called RLVR: reinforcement learning with verifiable rewards (though people sometimes use the term loosely when rubrics include LLM-judge checks).

You give the model a maximum number of steps or a timeout limit. The model will either hit the limit or it will say "I'm done."

And from there, we  have a set of output artifacts inside the environment.
For example, if the goal is to fill out an Excel model for finance, a sheet will be modified.

Then the grader - also called verifier - runs.
Its job is to evaluate the human-generated rubric.

The expert writing the rubric can put in a mix of objective and subjective aspects.

- **Deterministic** checks, like, are the numbers correct in the right places? Did the model mention what we told the model to mention? Did the model find the right data in the right places?
- **LLM judge** checks: another LLM evaluates subjective parts of the rubric, giving a score. For example, if the model made a bar chart, is it well formatted?

For math, you can formalize correctness of some tasks in Lean, though a lot of practical setups use simpler graders. For other domains, maybe a lot of knowledge is not formalized. How can you make decision trade-offs? How does a real scientist operate? What is their intuition about different work that they do? You make the rubrics to bake in these intuitions.

Implementation-wise, the rubric looks like a JSON file with a list of checks. Deterministic checks contain a reference to a Python function, and LLM judge checks contain a prompt for the grader LLM.

There can be 100-200 checks for a single task, so the models get a detailed score, like 120/183. That's what goes into GRPO.

After a training run, you also check whether the model improved on a held-out test set of tasks.

Because the model is literally trained to the rubric, the rubric has to be really, really good.

### Domains of RL Environments

The big labs are going to spend a lot of money to have people make these Docker container environments, because that's the path toward automating jobs. So that's what startups are working on.

What are the domains people are targeting these days?

1. **End-to-end coding** - the software development life cycle.
2. **Whole-company simulation.** They take a whole company with all of the company's history of Jira tickets, Confluence, emails, Slack messages, and you create tasks based on realistic work that has been done historically in this company. Sometimes, people get this data from failed startups, where it no longer serves any other purpose.
3. **Specialized knowledge work**: domains like finance, accounting, healthcare. They will hire people to generate these Docker environments.
4. **Hard math and science**: material science, biology, physics, and computer science itself, including AI research itself.

Those are the domains that people are mostly working with when we're talking about RL environments.

There's also robotics (a burgeoning field) and things like gaming.

## Recap

To recap, this is how RL environments work:

1. Start with a model that already has baseline agentic capabilities (after pre-training, SFT, and earlier post-training).
2. Put it in many specialized Docker environments with realistic tasks.
3. Score each rollout with a detailed human-authored rubric.
4. Feed those scores into GRPO, update the model, and repeat.
5. Run this loop for a couple of days, then evaluate on held-out tasks.
6. Repeat per domain/task family you want the model to improve on.

## What this means if you're an engineer

- RL environments are very lucrative right now because they produce what the frontier labs want now. There are dozens of companies doing this.
- RL environments require a substantial amount of engineering work to scale at quality, but it's not the most technically challenging work. A lot of the work is:
    - Calibration. Recall that you want these tasks to land in that middle band of difficulty. A lot of it is mucking with the task to calibrate its difficulty.
    - Random data work and data cleaning
    - Automating as much as possible to reduce the expert contractors' time.
- To work in this space as an engineer, you don't need much ML knowledge. You need to be a good engineer and know how to use agents well.
- If you work on RL environments, it's easy to get a job at a frontier lab because you've worked on their input data. It is a logical next step to become one of the researchers training on them.
