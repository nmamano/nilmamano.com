I've been using [Claude Code](https://docs.anthropic.com/en/docs/claude-code) as my primary coding tool. The main friction? Terminal management, especially when some tasks can only be done remotely via ssh (like [model training](/blog/wall-game-ai)).

Tmux helped; cmux was a clear improvement. For reference, this is my cmux setup: one horizontal tab per main project, with multiple vertical panes (and tabs) per project:

<BlogImage src="/blog/isomux/cmux-setup.png" alt="cmux setup with multiple panes and tabs" />

Skill issue, I know, but trying to keep good uptime on multiple agents felt a bit claustrophobic.

Isomux is my solution: an office metaphor for agents, with isometric graphics for the nostalgia hit.

Please see it in action at [isomux.com/demo](https://isomux.com/demo) before reading on.

<BlogImage src="/blog/isomux/cover.png" alt="Isomux office view with agents at desks" />

Each agent sits at a desk. You see who is working, who's idle (sleeping), and who needs you (hand raised) at a glance.

The thesis is that by anthropomorphizing agents, we reduce cognitive load; we're more used to coordinating humans than terminals.

This post dives into the architecture. We'll trace how isomux:

- bootstraps a Claude Code session from the Agent SDK,
- injects per-agent identity and working directory via launcher scripts,
- multiplexes all agent events over a single WebSocket,
- derives agent state from SDK stream events,
- handles abort and session recovery for a tricky race condition,
- enforces safety hooks as pre-tool-call middleware, and
- keeps the browser in sync with a Redux-like store.

The full source is on [GitHub](https://github.com/nmamano/isomux). It's free, open source, and designed with self-hosting in mind.

<Callout>
Isomux was built by Claude Code agents running inside isomux since the first version was working, a few commits in. Developing a dev tool from itself is fun!
</Callout>

## Architecture Overview

Isomux is a **single Bun process** that serves the UI, manages agents in-process via the SDK, and talks to browsers over WebSocket. There's no database - just in-memory state backed by flat files.

| Component | Role |
|---|---|
| **Bun HTTP server** | Serves the React UI as static files |
| **WebSocket layer** | Bidirectional communication: commands from browsers, events from agents |
| **Agent Manager** | Spawns/kills agents via the Claude Agent SDK, consumes SDK streams, derives state, emits events; enforces safety hooks as pre-tool-call middleware |
| **Persistence** | Append-only session logs, agent config, and an inter-agent discovery manifest - all flat files, no database |
| **React UI** | Isometric office view (SVG), conversation view, embedded terminal |
| **Landing page** | [isomux.com](https://isomux.com) - project homepage with interactive demo |

The server process is the single source of truth. Browsers are stateless relays - when one connects, the WebSocket `open` handler sends it a `full_state` snapshot, and from there incremental events keep it in sync. Multiple browsers (laptop, phone, another tab) all see the same thing in real time.

```
Browser A  ──┐                      ┌── Agent 1 (SDK session)
Browser B  ──┼── WebSocket ── Bun ──┼── Agent 2 (SDK session)
Phone      ──┘              server  └── Agent 3 (SDK session)
```

## The Agent Lifecycle

### Spawning agents

When you click an empty desk to spawn an agent, you can provide:

- a name,
- a working directory (`cwd`), which is important for things like `CLAUDE.md`, git context, and MCP servers defined in that directory.
- a model,
- an agent-specific system prompt

The browser sends a `spawn` command to the server, which:

1. Creates a **launcher script**,
2. Initializes the SDK session,
3. Emits an `agent_added` event to all browsers.

There's a problem: Claude SDK's `SDKSessionOptions` doesn't expose fields for `cwd` or `appendSystemPrompt` - those are CLI flags. Isomux works around this by generating a per-agent `.mjs` launcher script.

A `.mjs` file is a JavaScript file using ES module syntax, which is needed here for the top-level await:

```typescript
// ~/.isomux/launchers/AGENT_ID.mjs

// sets the working directory
process.chdir(...)

// injects the agent identity, office context, office prompt, and custom
// instructions
process.argv.push("--append-system-prompt", ...)

// boots the Claude Code CLI, which picks up the modified cwd and argv
await import("isomux/node_modules/@anthropic-ai/claude-agent-sdk/cli.js")
```

The launcher changes `process.cwd()` and injects `--append-system-prompt` into `process.argv` before importing the Claude Code CLI entry point. This is passed to `createSession` as `pathToClaudeCodeExecutable`:

```typescript
// server/agent-manager.ts
function createSession(managed: ManagedAgent, resumeSessionId?: string) {
  const opts = {
    model: managed.info.model,
    permissionMode: managed.info.permissionMode,
    pathToClaudeCodeExecutable: managed.launcherPath,
    hooks: createSafetyHooks(),
  };
  return resumeSessionId
    ? unstable_v2_resumeSession(resumeSessionId, opts)
    : unstable_v2_createSession(opts);
}
```

This is admittedly a hack - it relies on the SDK spawning the launcher as a subprocess - but works reliably.

<Callout>
The SDK's V2 API (`unstable_v2_createSession`) is in alpha, which means working around missing features, undocumented behavior (the abort race condition mentioned below), and likely breaking changes. But full Claude Code sessions with tools, MCP servers, and project context, managed programmatically, made it worthwhile.
</Callout>

### Agent identity

The system prompt looks like this, but with the parameters expanded:

```
You are AGENT_NAME, one of the agents in the Isomux office. Your goal is to help
the office boss, who talks to you in this chat.

To discover other office agents and their conversation logs, read
~/.isomux/agents-summary.json.

USER_DEFINED_OFFICE_WIDE_SYSTEM_PROMPT

USER_DEFINED_AGENT_SPECIFIC_SYSTEM_PROMPT
```

The system prompt is designed to be brief, but leaves breadcrumbs so the agent can load in more state if it needs to.

In the mentioned agent summary doc, the agent can find metadata about itself and every other agent:

```
// ~/.isomux/agents-summary.json.

{
  "id": "agent-1774819851476-qmpf",
  "name": "PersonalSiteAgent",
  "desk": 7,
  "room": 1,
  "topic": "Write technical blog post about isomux",
  "cwd": "~/nilmamano.com",
  "model": "claude-opus-4-6",
  "logDir": "~/.isomux/logs/agent-1774819851476-qmpf"
},
```

Further, through the `logDir` paths, it has access to the current conversation of every agent (i.e., since the last `/clear`, which works per-agent).

This means you can ask an agent, _"What do you think of OTHER_AGENT's approach?"_ and it just works - but we are getting ahead of ourselves.

### Agent persistence

The `~/.isomux/` folder contains:

- `agents.json`: full agent config, including things like the outfit choices and the agent-specific system prompt.
- `agents-summary.json`: a lightweight version linked to all agents in their system prompt, so they can discover each other.
- `logs/{agentId}/{sessionId}.jsonl`: append-only JSONL files for conversation history. Each line is a `LogEntry`.
- `office-prompt.txt`: user-defined office-wide system prompt injected into all agents.
- `todos.json`: shared office todo list.
- `launchers/`: the per-agent .mjs launcher scripts discussed above.
- `recent-cwds.json`: recently used working directories (for autocomplete in the spawn dialog)

These files are kept consistent with the state sent to the clients.

When a browser first connects, it receives a `full_state` snapshot containing every agent, their logs, slash commands, and office-wide settings. From there, incremental events keep it in sync.

On server restart, agents are restored from `agents.json` and their SDK sessions are recreated.

Past conversations can be resumed from the JSONL logs with `/resume` or by right-clicking an agent. This makes the `/resume` interaction per-agent, unlike in Claude Code.

Isomux persists every conversation forever by design. My `~/.isomux/` is 22MB. You never know when it could be useful.

## The WebSocket Multiplexer

The server talks to connected browsers via web sockets.

- The server notifies all browsers of state updates via a single `broadcast` function.
- The clients give commands to the server, which are handled in `handleCommand()`:

```typescript
// server/index.ts

async function handleCommand(cmd: ClientCommand) {
  switch (cmd.type) {
    case "send_message":
      // Don't await — let it stream in the background
      AgentManager.sendMessage(cmd.agentId, cmd.text, cmd.username);
      break;
    case "spawn":
      await AgentManager.spawn(cmd.name, cmd.cwd, cmd.permissionMode, cmd.desk, ...);
      break;
    // ...
  }
}
```

The `send_message` command - where a user sends a message to the LLM - is deliberately not awaited. Calling it without `await` kicks off the async work and returns immediately, so the event loop stays free to process other commands (spawns, aborts, messages to other agents, etc.) while the SDK streams the response in the background. Most other command types are handled synchronously.

## Streaming and State Derivation

### Consuming the SDK Stream

When a message is sent to an agent, `consumeStream` enters an async loop that reads SDK events and converts them into log entries:

```typescript
// agent-manager.ts
async function consumeStream(agentId: string, managed: ManagedAgent) {
  const gen = managed.streamGeneration;
  managed.streaming = true;
  try {
    for await (const msg of managed.session.stream()) {
      if (!agents.has(agentId) || gen !== managed.streamGeneration) break;
      processMessage(agentId, msg);
    }
  } catch (err: any) {
    // ... error handling (see abort recovery below) ...
  } finally {
    if (managed.streamGeneration === gen) {
      managed.streaming = false;
      managed.aborting = false;
    }
  }
}
```

The `streamGeneration` counter is the key to correctness here. When an abort happens mid-stream, a new `consumeStream` may start before the old one's `finally` block runs. Without the generation check, the old stream's cleanup would clobber the new stream's flags.

### State Machine

The isometric characters animate based on agent state: sleeping when idle, typing when thinking, waving when waiting for input. State is **derived from SDK events**, not explicitly tracked by the SDK:

```typescript
function deriveState(msg: SDKMessage): AgentState | null {
  switch (msg.type) {
    case "assistant": {
      const content = msg.message?.content;
      if (content.some((b: any) => b.type === "tool_use")) {
        return "tool_executing";
      }
      return "thinking";
    }
    case "tool_progress":
      return "tool_executing";
    case "result":
      return "waiting_for_response";
    default:
      return null;
  }
}
```

State transitions drive both the UI animations and the attention system: when an agent moves from a "working" state (`thinking`, `tool_executing`) to an "attention" state (`idle`, `error`, `waiting_for_response`) while you're looking at a different agent, it gets flagged with a notification dot.

### Abort and Session Recovery

There's a subtle race condition in the Agent SDK. When you abort a stream and then send a new message, the SDK can throw an "aborted by user" error on the *new* stream - a ghost from the previous abort. Worse, it may have internally buffered the `send()` call, causing an off-by-one: the response you get is for the *previous* message, not the one you just sent.

Isomux handles this by detecting the stale abort error and recreating the session:

```typescript
// Inside consumeStream's catch block
const isAbortError = /abort/i.test(err.message || "");
if (isAbortError) {
  console.warn(`Agent ${agentId}: post-abort stream error, recreating session`);
  try { managed.session?.close(); } catch {}
  managed.session = sessionId
    ? createSession(managed, sessionId)
    : createSession(managed);
  updateState(agentId, "waiting_for_response");
}
```

Recreating the session with the same `sessionId` preserves the conversation history while clearing the SDK's internal buffering state.

## Safety Hooks

I run all my agents in `bypassPermissions` mode. Isomux injects `PreToolUse` hooks into every SDK session that block dangerous commands before they execute.

1. **Git safety**: blocks destructive git commands.
2. **Filesystem safety**: blocks `rm -rf` on root/home paths while allowing it on temp directories.
3. **Isomux config protection**: blocks all writes to `~/.isomux/`, since that directory is managed by the server. Read operations are allowed (agents need to read `agents-summary.json` to discover each other).

## The Frontend

### Redux-Like Store

The React frontend uses a `useReducer` store where **server messages are actions**. The same `ServerMessage` types that flow over the WebSocket are dispatched directly into the reducer:

```typescript
// store.tsx
export function StoreProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(reducer, initialState);

  useEffect(() => {
    connect((msg: ServerMessage) => {
      dispatch(msg as Action);  // Server messages are actions
    });
  }, []);
}
```

This eliminates the usual action-creator boilerplate. The reducer handles `agent_added`, `agent_updated`, `log_entry`, `full_state`, and other server events directly.

The store also manages local-only state: input drafts (preserved when switching between agents), attention tracking, and the focused agent.

### Attention tracking and notifications

The attention system is simple but effective. An agent "needs attention" when it transitions from a working state to a terminal state while the user is looking at a different agent:

```typescript
// In the reducer
if (wasWorking && state.focusedAgentId !== action.agentId) {
  needsAttention.add(action.agentId);
}
```

On the office view, agents needing attention get a pulsing indicator. Combined with sound notifications (when the browser tab is hidden), you never miss when an agent finishes or gets stuck.

### Keyboard navigation

Ergonomics are important. The keyboard shortcuts I use the most are:

- Tab and Shift+Tab to rotate conversations between agents in the room.
- Hold Ctrl+Space for voice-to-text prompting.

On mobile, left and right swipe gestures replace Tab and Shift+Tab.
