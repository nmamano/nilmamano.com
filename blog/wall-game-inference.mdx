In a [previous post](/blog/wall-game-ai), I described the AlphaZero-style AI behind [wallgame.io](https://wallgame.io) at the architectural level: MCTS, the neural network, training via self-play, and inference batching.

This post zooms in the inference piece. We'll trace the path a single inference request takes through the codebase, from the moment an MCTS coroutine needs a position evaluated to the moment the GPU result arrives back.

The inference pipeline is shared between training (self-play) and production (users playing vs the AI). During self-play, requests from hundreds of parallel games are batched together; in production, requests from concurrent games with different users do the same.

## Prerequisites and Concepts

### Coroutines

Our batching model relies on **C++20 coroutines**: functions that can suspend partway through and resume later, potentially on a different thread.

Unlike regular functions, whose stack frames live on the thread's call stack (and are therefore tied to that thread), a coroutine's state is allocated on the heap. This means no thread needs to "hold onto" a suspended coroutine - any thread can resume it later.

A coroutine looks mostly like a normal function, but it has access to a special keyword:

- `co_await expr`: suspends the coroutine until `expr` produces a result. The coroutine's state (local variables, where it left off) is saved to the heap, and the thread it was running on is freed to do other work. When the result is ready, the coroutine resumes right after the `co_await`.

<Callout title="Key design principle">
For AlphaZero-style AIs, the main loop consists of traversing the MCTS tree down to a leaf, running a model inference to evaluate the leaf position, and backpropagating the result up the tree. This can be encapsulated as a co-routine that `co_await`'s at the inference step.

The tree traversals and updates are computationally cheap relative to the GPU inference, so a small pool of 10-20 CPU threads is enough to keep hundreds of coroutines in flight and produce enough inference requests to sustain ~100% utilization on a GPU such as an RTX5090. Each suspended coroutine only consumes a bit of heap memory.
</Callout>

### Promises and Futures

The inference pipeline needs a way for a coroutine on the thread pool to request GPU work and get the result back without blocking a thread.

For this, we use **promises** and **futures** (`folly::Promise`, `folly::SemiFuture`), which form a one-shot channel for passing a result between threads. The producer writes to the `Promise`; the consumer `co_await`'s the `SemiFuture`.

In our pipeline:

1. The coroutine (running on a thread pool thread) creates a `Promise<ModelOutput>` and calls `getSemiFuture()` on it. This returns a `SemiFuture<ModelOutput>` linked to the same shared state.
2. The `Promise` is handed to the GPU worker (by wrapping it inside an `InferenceTask` and putting that task in a queue for the GPU worker).
3. The coroutine calls `co_await` on the `SemiFuture`. This **suspends** the coroutine without blocking the thread. Under the hood, `co_await` registers a callback on the shared state: "when the result arrives, post this coroutine's resumption to the thread pool."
4. Later, the GPU worker calls `promise.setValue(result)`. This stores the result in the shared state and fires the callback, which posts the coroutine's resumption to the thread pool's work queue.
5. A thread pool worker picks up the coroutine and resumes it right after the `co_await`, with the result now available.

### Libraries

Our inference pipeline uses the following:

- **[Folly](https://github.com/facebook/folly)** (Facebook Open-source Library) is Meta's C++ foundation library. C++'s coroutine support is barebone, so we rely on Folly for the runtime. Here's what we use from it:
    - **`CPUThreadPoolExecutor`**: A thread pool. Coroutines are bound to an executor and resume on whichever thread is free.
    - **`folly::coro::Task<T>`**: The return type for coroutines. It wraps the heap-allocated coroutine state and integrates with the executor, so when the coroutine is ready to run (or resume), it gets posted to the thread pool's work queue.
    - **`collectAllWindowed(tasks, maxConcurrency)`**: A utility that runs a collection of tasks (coroutines) with a bounded concurrency - start up to `maxConcurrency`, and as each one completes, start the next.
    - **`folly::Promise` and `folly::SemiFuture`**: See [above](#promises-and-futures).
    - **`MPMCQueue`**: A bounded, lock-free multi-producer multi-consumer queue. Used to pass inference requests from coroutines to the GPU worker without mutex contention.
    - **`EvictingCacheMap`**: An LRU cache. Used to cache position evaluations so repeated positions skip the GPU.

<Callout>
In our pipeline, `collectAllWindowed` is used to bound how many coroutines work in parallel in the same MCTS tree. For example, we may want to collect 1000 MCTS samples to build the MCTS tree at a given position (i.e., launch 1000 coroutines), but only run up to 4 at a time **even though technically all 1000 could run concurrently with just a few threads**. This is because each sample refines the tree, so each sample benefits from previous ones. Launching all 1000 concurrently would result in some of them trying to explore the same leaves, resulting in wasted (duplicated) inferences and thus a weaker evaluation of the position.

During self-play, we can play 256+ games in parallel, which fills the inference batches without needing parallel samples for the same game.
</Callout>

- **[TensorRT](https://developer.nvidia.com/tensorrt)** is NVIDIA's inference optimizer. It takes a trained neural network (exported from PyTorch as ONNX) and compiles it into a GPU-optimized execution plan: fusing layers, choosing the fastest kernel implementations for the specific GPU, and optimizing memory layout. We use TensorRT rather than running PyTorch directly because inference latency matters - TensorRT is typically 2-5x faster for our model size.

- **CUDA** is NVIDIA's GPU programming toolkit. We don't write custom CUDA kernels - TensorRT handles that - but we use CUDA's memory management APIs to move data between CPU and GPU efficiently. A few CUDA concepts that come up later:
    - **Pinned memory**: Memory allocated with `cudaMallocHost` that the OS is prevented from paging out to disk. This allows the GPU to transfer data directly via DMA (Direct Memory Access) over the PCIe bus, skipping an extra copy that normal memory requires.
    - **CUDA stream**: A sequence of GPU operations (memory transfers, kernel launches) that execute in order. Operations on the same stream are guaranteed to run sequentially; the CPU queues them without waiting.
    - **Synchronize**: Block the CPU thread until all operations on a CUDA stream have completed.

## The Pipeline in Five Steps

Here's the full lifecycle of a single inference request:

1. An MCTS coroutine calls `inference()`, gets a `SemiFuture`, and suspends on `co_await`.
2. The request enters a lock-free `MPMCQueue`.
3. A dedicated GPU worker thread pulls a batch from the queue and runs inference.
4. The GPU worker fulfills each `Promise` with the GPU results.
5. Folly reschedules the suspended coroutines back onto the thread pool.

Let's walk through each step with the actual code.

## CPU Overview

Before diving in, it helps to know what threads are running and who does what. The engine has three kinds of threads:

- **Thread pool** (`folly::CPUThreadPoolExecutor`): A pool of 10-20 general-purpose worker threads that run MCTS coroutines: they traverse down an MCTS tree until they reach a leaf that needs evaluation, suspend (`co_await`) until inference finishes, and then backpropagate the outcome up the tree. These threads are interchangeable; any thread can resume any coroutine. When a coroutine suspends on `co_await`, the thread is immediately available for other coroutines. There are typically far more coroutines than threads - during self-play, hundreds of coroutines may be suspended waiting for GPU results while only 8-12 threads actively run. The coroutines are not pooled; they're created on demand by `collectAllWindowed` and destroyed when they complete.
- **GPU worker thread(s)** (`std::jthread`): Dedicated threads that own the GPU. Each GPU worker runs a tight loop: drain requests from the queue, copy states into a pinned memory buffer, call TensorRT, and fulfill the promises with results.
- **Main thread**: Sets everything up and kicks off the work. What it does after that depends on the mode:
    - **Training:** Blocks on `folly::coro::blockingWait` until all self-play games finish. Then the program ends and the training script (which uses PyTorch) picks up the data from the self-play games for training. 
    - **Production:** Runs a `folly::EventBase` event loop, reading JSON requests from stdin and dispatching them to the live-game session manager.


<Callout title="Parallel samples within a single game">

Multiple coroutines can traverse the same MCTS tree in parallel, allowing the engine to spend more computational resources to make the AI stronger or faster in a single game.

The MCTS tree uses node-level concurrency control to handle this: `TreeNode::value` and `TreeEdge::active_samples` are `std::atomic`, so concurrent updates don't corrupt the tree. To prevent parallel samples from all going down the same branch, each sample temporarily increments an `active_samples` counter on the edges it traverses. The UCB formula penalizes edges with active samples, steering other samples toward less-explored branches. This is a variant of the technique known as _virtual loss_ in the MCTS literature.

The downside is diminishing returns: with many parallel samples, they increasingly interfere with each other, exploring redundant branches despite the virtual loss penalty. During self-play, where throughput matters more than per-game quality, it's more efficient to run many games with fewer parallel samples each. In production, where we want the strongest play for a single game, more parallel samples are worthwhile.

</Callout>

A dedicated GPU worker thread (rather than having coroutines call TensorRT directly) serves two purposes. First, batching: the GPU is most efficient processing many positions at once, but each coroutine only has one position. The worker thread collects positions from many coroutines into a single batch. Second, isolation: TensorRT calls block until the GPU finishes, and we don't want to tie up thread pool threads with GPU waits.

## Step 1: The Coroutine Calls inference() and Suspends

Everything starts in the MCTS search tree. When a sample reaches an unexplored leaf node, it needs the neural network to evaluate the position. This happens in `create_tree_node`:

```cpp
Evaluation eval = co_await m_evaluate(board, turn, previous_position);
```

The `m_evaluate` function is a coroutine-returning callable:

```cpp
std::function<folly::coro::Task<Evaluation>(...)>
```

In both training and production, it's a stack of four layers:

```
CachedPolicy         →  Check LRU cache; on miss, forward to:
  BatchedModelPolicy   →  Convert board to tensor, then:
    BatchedModel         →  Queue the request, return SemiFuture  ── thread pool suspends here
      TensorRTModel        →  Run the GPU kernel                  ── GPU worker thread
```

### Cache Layer

MCTS frequently revisits the same positions. Parallel samples from the same game can reach the same leaf, and across self-play games, common openings repeat constantly. Without caching, these would all become redundant GPU evaluations.

The `CachedPolicy` uses sharded `folly::EvictingCacheMap` instances to avoid this.

<Callout>
**Why sharded?** A single cache with one lock would serialize all lookups across all threads in the thread pool. Instead, we hash each position and route it to one of `N` shards (roughly matching the thread pool size), each with its own lock. This way, threads accessing different shards never contend.
</Callout>

```cpp
// cached_policy.cpp
folly::coro::Task<Evaluation> CachedPolicy::operator()(
    Board const& board, Turn turn,
    std::optional<PreviousPosition> previous_position) {

    CacheEntryView ce_view{board, turn, previous_position};
    auto hash = folly::HeterogeneousAccessHash<CacheEntry>{}(ce_view);
    auto& lru = m_cache->lrus[hash % m_cache->lrus.size()];

    {
        auto locked_lru = lru.wlock();
        auto existing_entry = locked_lru->find(ce_view);
        if (existing_entry != locked_lru->end()) {
            ++m_cache->cache_hits;
            co_return existing_entry->second;  // HIT: skip the GPU entirely
        }
    }

    Evaluation eval = co_await m_cache->evaluate(board, turn, previous_position);
    lru.wlock()->insert(CacheEntry{board, turn, previous_position}, eval);
    ++m_cache->cache_misses;
    co_return eval;
}
```

On a cache miss, we fall through to `BatchedModelPolicy`.

`BatchedModelPolicy` converts the board into the neural network's input format - 8 or 9 float planes (described in the [AI post](/blog/wall-game-ai#input-encoding)) - and then calls `BatchedModel::inference()`:

### The Handoff: Promise and SemiFuture

Here's where the coroutine actually suspends. `BatchedModel::inference()` is *not* a coroutine - it's a regular function. Its job is to drop a request in the queue and hand back a `SemiFuture` so the *caller* can wait. It creates a `Promise`/`SemiFuture` pair, enqueues the request, and returns immediately:

```cpp
// batched_model.cpp
folly::SemiFuture<ModelOutput> BatchedModel::inference(std::vector<float> states) {
    InferenceTask task{std::move(states), {}};
    auto result = task.output.getSemiFuture();

    m_tasks.blockingWrite(std::move(task));

    return result;
}
```

The `InferenceTask` bundles the input state with a `Promise<ModelOutput>`:

```cpp
// batched_model.hpp:40-43
struct InferenceTask {
    std::vector<float> state;
    folly::Promise<ModelOutput> output;
};
```

Back in `BatchedModelPolicy`, the `co_await` on the returned `SemiFuture` does two things:
1. Saves the coroutine's stack frame (local variables, instruction pointer) to the heap.
2. Returns control to the Folly executor, freeing the thread.

The coroutine is now suspended. It consumes no CPU but its state persists in memory, waiting for the `Promise` to be fulfilled.

## Step 2: The Request Enters the MPMCQueue

The `InferenceTask` is now sitting in `m_tasks`, a `folly::MPMCQueue<InferenceTask>` - a lock-free multi-producer multi-consumer queue.

```cpp
// batched_model.hpp:45
folly::MPMCQueue<InferenceTask> m_tasks;
```

This queue is the bridge between the MCTS world (many coroutines producing one request each) and the GPU world (one worker consuming them in batches).

We need a queue that handles tens of concurrent writers without serializing them behind a mutex. Folly's `MPMCQueue` is lock-free: writers and readers use atomic operations rather than locks, so concurrent writes don't block each other. It's also bounded (default capacity: 4,096 slots), which provides natural backpressure - `blockingWrite` only blocks if the queue is full, which means the GPU can't keep up. This prevents unbounded memory growth if requests arrive faster than the GPU can process them.

## Step 3: The GPU Worker Pulls a Batch and Runs Inference

A dedicated worker thread runs in a loop, filling batches and sending them to the GPU:

```cpp
// batched_model.cpp
void BatchedModel::run_worker(std::size_t idx) {
    std::vector<folly::Promise<ModelOutput>> dequeued_promises;

    PinnedBuffer<float> states(m_models[idx]->batch_size() * m_models[idx]->state_size());
    PinnedBuffer<float> priors(m_models[idx]->batch_size() * m_models[idx]->prior_size());
    PinnedBuffer<float> values(m_models[idx]->batch_size());

    while (true) {
        for (int i = 0; i < m_models[idx]->batch_size(); ++i) {
            InferenceTask task;

            if (i == 0) {
                m_tasks.blockingRead(task);      // Block until at least one arrives
            } else if (!m_tasks.read(task)) {
                break;                           // Non-blocking: take what's available
            }

            if (task.state.empty()) {
                return;                          // Sentinel: shutdown signal
            }

            std::ranges::copy(task.state, states.data() + m_models[idx]->state_size() * i);
            dequeued_promises.push_back(std::move(task.output));
        }

        m_models[idx]->inference(states, {priors, values});    // GPU kernel

        for (std::size_t i = 0; i < dequeued_promises.size(); ++i) {
            std::vector<float> prior{
                priors.data() + m_models[idx]->prior_size() * i,
                priors.data() + m_models[idx]->prior_size() * (i + 1)};

            dequeued_promises[i].setValue(ModelOutput{std::move(prior), values[i]});
        }

        m_batches += 1;
        m_inferences += dequeued_promises.size();
        dequeued_promises.clear();
    }
}
```

There's a lot going on here. Let's break it down.

### Greedy Batching

The first task blocks the thread (`blockingRead`). Once one arrives, the worker greedily tries to grab more via non-blocking `read()` calls, up to `batch_size`. This means the batch size is dynamic: if 200 requests are queued, the worker fills the whole batch; if only 3 are available, it runs a batch of 3. No artificial delays.

We don't wait for a full batch because latency matters. If only 3 requests are in the queue and we wait for 253 more, those 3 coroutines stall. The GPU is less efficient with small batches, but the throughput lost is small compared to the latency saved. During self-play the queue is rarely empty.

### Pinned Memory Buffers

The `PinnedBuffer<float>` arrays are allocated with `cudaMallocHost`, which pins the memory in physical RAM, preventing the OS from paging it out to disk.

<Callout>
Normal (pageable) memory requires CUDA to first copy data to an internal pinned staging buffer before initiating the DMA transfer to the GPU - an extra copy on every batch. Pinned memory eliminates this step, enabling direct DMA transfers over PCIe. The pinned buffers are allocated once when the worker starts and reused across batches, so we pay the allocation cost only once.
</Callout>

```cpp
// cuda_wrappers.hpp:37-38
PinnedBuffer(std::size_t size) : m_size{size} {
    cuda_check(cudaMallocHost(&m_data, size * sizeof(T)));
```

### The GPU Kernel

`m_models[idx]->inference(states, {priors, values})` calls through to the TensorRT model:

```cpp
// tensorrt_model.cpp
void TensorRTModel::inference(std::span<float> states, Output const& out) {
    m_states.to_device(states, m_stream);       // Async host → device transfer
    m_context->enqueueV3(m_stream.get());       // Queue the GPU kernel
    m_priors.to_host(out.priors, m_stream);      // Async device → host transfer
    m_values.to_host(out.values, m_stream);      // Async device → host transfer
    m_stream.synchronize();                      // Wait for everything to complete
}
```

All four operations are enqueued on the same CUDA stream, so they execute sequentially on the GPU without requiring synchronization between each step. The CPU-side calls return almost instantly - they just queue work. Only `synchronize()` blocks the worker thread, waiting for the entire upload-compute-download sequence to finish. Meanwhile, the MCTS coroutines continue running on the CPU thread pool - only the GPU worker thread is blocked.

The `CudaBuffer` class wraps `cudaMemcpyAsync` for the transfers:

```cpp
// cuda_wrappers.hpp
void to_device(std::span<T> in, CudaStream& stream) {
    cuda_check(cudaMemcpyAsync(m_device_ptr, in.data(), in.size() * sizeof(T),
                               cudaMemcpyHostToDevice, stream.get()));
}
```

## Step 4: The Worker Fulfills Each Promise

After the GPU returns, the worker iterates over `dequeued_promises` and calls `setValue` on each:

```cpp
dequeued_promises[i].setValue(ModelOutput{std::move(prior), values[i]});
```

Each promise is fulfilled with its corresponding slice of the output batch. The `setValue()` call transitions the promise to the "fulfilled" state and triggers the associated `SemiFuture`'s continuation machinery.

## Step 5: Coroutines Resume on the Thread Pool

When `setValue()` is called, Folly checks if any coroutine is waiting on the associated `SemiFuture`. If so, it schedules the coroutine's resumption as a task on the executor (a `folly::CPUThreadPoolExecutor`).

The coroutine doesn't resume immediately on the GPU worker thread - instead, a lightweight callback is posted to the thread pool's task queue. When a thread pool worker picks it up, it restores the coroutine's saved state and resumes execution right after the `co_await`, with the `ModelOutput` result now available.

This separation is key: the GPU worker thread stays focused on batching and inference, while coroutine execution happens on the CPU thread pool.

### Post-Processing: From Raw Output to MCTS Priors

Back in `BatchedModelPolicy`, the coroutine resumes with the raw model output and converts it into something MCTS can use:

```cpp
// batched_model_policy.cpp
    Evaluation eval;
    eval.value = inference_result.value;

    // Add legal pawn moves with their priors
    add_pawn_moves(Pawn::Cat, board.position(turn.player), int(wall_prior_size));
    if (board.allows_mouse_moves()) {
        // ... add mouse moves too
    }

    // Add legal wall placements with their priors
    for (Wall wall : board.legal_walls()) {
        int index = int(wall.type) * board.columns() * board.rows()
                  + board.index_from_cell(wall.cell);
        eval.edges.emplace_back(wall, inference_result.prior[index]);
        total_prior += inference_result.prior[index];
    }

    // Renormalize to account for illegal actions
    for (TreeEdge& edge : eval.edges) {
        edge.prior /= total_prior;
    }

    co_return eval;
```

The model outputs probabilities for *all* positions (legal and illegal). This step filters to only legal actions and renormalizes so the priors sum to 1.

The result flows back through the cache layer (which stores it for future lookups), and finally arrives at `create_tree_node` in `mcts.cpp`, where the new tree node is created with the evaluated priors and value.

## Parallel Samples: Filling the Batch

A single MCTS sample produces one inference request. To fill batches of 256, we need many concurrent requests. This is where `collectAllWindowed` comes in:

```cpp
// mcts.cpp
folly::coro::Task<float> MCTS::sample(int samples) {
    m_samples_done = 0;
    auto* executor = co_await folly::coro::co_current_executor;
    auto sample_tasks = views::iota(0, samples) |
        views::transform([&](int) { return single_sample().scheduleOn(executor); });

    co_await folly::coro::collectAllWindowed(sample_tasks, m_opts.max_parallelism);

    TreeNode::Value val = m_root->value;
    co_return val.total_weight / val.total_samples;
}
```

This creates `samples` coroutines (e.g., 1,200) but only allows `max_parallelism` to run concurrently (e.g., 32). Each running coroutine traverses the tree, reaches a leaf, suspends on `co_await` for GPU evaluation, and frees its thread for another coroutine. At any given moment, there are many suspended coroutines waiting for GPU results, which is exactly what fills the inference batch.

## Training vs Production

Both training and production construct the same four-layer policy stack:

```
CachedPolicy → BatchedModelPolicy → BatchedModel → TensorRTModel
```

The setup code is almost identical. Here's training:

```cpp
// main.cpp
std::vector<std::unique_ptr<Model>> tensor_rt_models;
int num_models = mode == Mode::Train ? 2 : 1;
for (int i = 0; i < num_models; i++) {
    tensor_rt_models.push_back(std::make_unique<TensorRTModel>(engine));
}
auto batched_model = std::make_shared<BatchedModel>(
    std::move(tensor_rt_models), kBatchedModelQueueSize);
BatchedModelPolicy batched_model_policy(std::move(batched_model), FLAGS_boost_mouse_priors);
return CachedPolicy(std::move(batched_model_policy), FLAGS_cache_size);
```

And production:

```cpp
// bgs_engine_main.cpp
std::vector<std::unique_ptr<Model>> models;
auto tensor_model = std::make_unique<TensorRTModel>(engine);
models.push_back(std::move(tensor_model));

auto batched_model = std::make_shared<BatchedModel>(
    std::move(models), kBatchedModelQueueSize);
BatchedModelPolicy batched_model_policy(std::move(batched_model));
eval_fn = CachedPolicy(std::move(batched_model_policy), FLAGS_cache_size);
```

| | Training | Production |
|---|---|---|
| **TensorRT model instances** | 2, each with its own GPU worker thread | 1 per engine process |
| **Concurrent games** | Hundreds of self-play games on a thread pool | Concurrent BGS sessions against human players |
| **What happens with results** | MCTS visit counts become training data (exported to CSV) | MCTS picks the best move and sends it to the game server |

Training uses 2 TensorRT execution contexts (each with its own CUDA stream and GPU worker thread) to pipeline GPU work. While one worker blocks on `synchronize()` waiting for the GPU to finish a batch, the other can be copying the next batch's data to the GPU. This keeps the GPU busier than a single worker could, since the worker spends a nontrivial fraction of its time on CPU-side bookkeeping (draining the queue, copying states into the pinned buffer, fulfilling promises).

In production, we currently deploy 3 different models (5x5, 8x8 Classic, 8x8 Standard), each as a separate engine process with its own `BatchedModel` and GPU worker. A single worker per model is sufficient because live games generate far fewer inference requests than self-play.

### Training: Self-Play Loop

During training, a `CPUThreadPoolExecutor` runs many self-play games concurrently as coroutines. Each game has two MCTS instances (one per player) sharing the same batched model. Coroutines from different games interleave naturally - when one suspends for GPU evaluation, another runs on its thread:

```cpp
// play.cpp:94-111
folly::coro::Task<GameResult> training_play_single(
    Board const& board, EvaluationFunction evaluate1,
    EvaluationFunction evaluate2, int index, TrainingPlayOptions opts) {

    MCTS mcts1{evaluate1, board, {.max_parallelism = opts.max_parallel_samples, ...}};
    MCTS mcts2{evaluate2, board, {.max_parallelism = opts.max_parallel_samples, ...}};

    for (int num_moves = 1; ...; ++num_moves) {
        for (int i = 0; i < 2; ++i) {
            co_await mcts1.sample(opts.samples);
            auto action = mcts1.commit_to_action(opts.temperature);
            mcts2.force_action(*action);
            // ...
        }
    }
}
```

After each game, the MCTS visit counts are converted to training targets:

```cpp
// state_conversions.cpp:110-128
void TrainingDataPrinter::operator()(MCTS const& out, int index) const {
    for (NodeInfo const& node_info : out.history()) {
        ModelInput model_input = convert_to_model_input(node_info.board, node_info.turn);
        ModelOutput model_output =
            convert_to_model_output(node_info, score_for_red, m_winner_contribution);
        print_training_data_point(output_file, model_input, model_output);
    }
}
```

The model output is derived from MCTS search results, not from the neural network directly. Each action's prior becomes `visit_count / total_visits`, and the value blends the MCTS Q-value with the actual game outcome. This is the "expert" data the network learns from in the next training generation.

### Production: BGS Protocol

In production, the engine is a long-lived process handling concurrent games via the [BGS protocol](/blog/wall-game-ai#the-protocol). Each game session has its own MCTS tree, and all sessions share the same `CachedPolicy` and `BatchedModel`. The same queue-and-batch mechanism handles all concurrent live games.

## Wrapping Up

The inference pipeline is about 250 lines of C++ total (`batched_model.cpp`, `batched_model_policy.cpp`, and a slice of `mcts.cpp`), built on top of Folly's coroutine and concurrent data structure primitives. It's a clean separation of concerns: MCTS coroutines don't know about batching, the GPU worker doesn't know about MCTS, and the `MPMCQueue` bridges the two worlds without locks.

The key insight is that the same pipeline serves both training (billions of evaluations across thousands of self-play games) and production (real-time play against humans) - the only thing that changes is what happens with the results.
